# M9: does the new compiler scale linearly with model size?

Measured on the branch `p2-m9`; the "before" binary is its base `7ca9d2c9`, the "after" binary
is the commit that adds this file. Both are `vera-next` built `-Doptimize=ReleaseFast` (native CPU).

## Method

- Models: `python3 tools/bench/gen_models.py wide N out.va` for N = 800, 1600, 3200, 6400
  (N parameters, N intermediate reals, one ternary per six rows).
- Command: `vera-next --emit-zig wideN.va -o out.zig` (spawns no `zig`).
- Clock: `tools/bench/rtime.c` (`zig cc -O2`), CPU = user + sys, peak = ru_maxrss. Min of 5 runs,
  under `flock ~/.cache/vera-heavy.1.lock`.
- Attribution: no `perf` on the build machine and valgrind cannot decode the native-CPU binary,
  so gdb stack samples (`gdb -p PID -batch -ex 'bt 80'` in a loop), bucketed by the
  pipeline job frame and, inside it, the hot function.
- Bytes: `--emit-zig` output and stderr byte-identical before and after at every size.

## Where the time went

Before, gdb samples (3200: 23 samples; 6400: 59):

- `Sema.eval.Env.init` under `Sema.decl.foldBody`: 22/23 at 3200, 57/59 at 6400 (about 97%).
  Every constant fold (`param.checkRange`, `param.literalBound`, `param.checkType`, and every
  `foldRef`) built a fresh `Env` whose `init` walks the module's whole parameter list and body into
  a hash map: O(module) per fold, one fold or more per parameter, O(N^2) in all.
- `Air.Float.Walk`: 1/23 and 0/59 of the time, but most of the peak: every `block` and `loop` frame
  allocated, and every `cond_br` copied, the whole slot state (one `Abstract`, 32 bytes, per
  variable). wide 6400 has about 1067 ternaries (blocks with a `cond_br`) and 6404 slots: about
  2 walks x 2 copies x 1067 x 6404 x 32 B = 875 MB of the 1074 MiB peak (an estimate from sizes;
  the peak after the fix is 39 MiB).
- The fixpoints the task named are not the cost: `Air.Setup` (one optimistic fixpoint) is not
  called on `vera-next`'s pipeline yet (only its tests and `diff-air-passes` run it), and
  `Float.Walk`'s fixpoint iterates only a `loop`'s body, which the wide model has none of.

After, wide 51200 (73 samples over 4 runs; 6400 is too short for gdb to sample):

| stage | share |
|---|---:|
| astgen | 25% |
| Air.Float.Walk | 25% |
| Air.Float, rest (tables, verdict) | 7% |
| Sema lowering (`semaAnalog`, `held`) | 29% |
| Sema parameter folds (`Env`) | 3% |
| codegen + write | 11% |

## The change

- `Sema`: a module's parameter layout (`eval.Layout`: each parameter's position, the aliases) is
  built once per instance (`Unit.layout`, in `Sema.arena`), with a copy of the instance's
  folded values (`Unit.values`). `decl.envOf` returns an `Env.initShared` that borrows both and
  copies the values only when a fold writes one (`Env.own`): a fold costs what it reads.
  Oracle: in Debug, `decl.checkLayout` builds the environment afresh as every fold did before and
  asserts the same positions, aliases and values.
- `Air.Float.Walk`: slot states are saved and joined through an undo trail (`States.trail`). A
  `cond_br` rolls back what its first arm wrote; a frame keeps, per slot written since it began,
  the slot's state at its start and the join so far; a loop's head is the slots some `repeat`
  wrote. Oracle: `States.dense`, the old whole-table copies, runs beside it in Debug
  (`Float.walk`) and every table (interval bits, NaN, domain, why) must agree.
